PROTEUS — MUTATION PROTOCOL v0.1

PURPOSE  
Give the first Cursor embodiment a disciplined way to modify project/source/host state without freezing Proteus into a rigid state machine. This is a safety and evidence protocol around mutations, not an ontology of the living process.

1\. MUTATION CLASSES  
CLASS P — project/source mutation inside C:\\Projects\\Proteus Git repository.  
CLASS H — host-incarnation mutation in Cursor/user/project configuration surfaces.  
CLASS M — project-mount mutation inside another project's workspace.  
CLASS C — cloud/developmental document proposal or promotion.

Every consequential mutation is tagged with one class or an explicit combination.

2\. REQUIRED PRE-MUTATION RECORD  
Before mutation record:  
\- RUN\_ID;  
\- target and mutation class;  
\- source requirement/evidence motivating it;  
\- intended behavioral effect;  
\- exact files/paths expected to change;  
\- current hashes/diff/status where feasible;  
\- backup/snapshot location;  
\- rollback command/procedure;  
\- relevant test/postcondition.

3\. BASELINE  
Baseline must capture enough reality to distinguish intended change from pre-existing state.

For project/source:  
\- Git branch/revision/status;  
\- untracked files;  
\- existing relevant config;  
\- current tests.

For Cursor host:  
\- Cursor version/build;  
\- actual discovered config paths;  
\- relevant file contents or secure checksums/backups;  
\- active workspace;  
\- plugin/rules/hooks/MCP surfaces present;  
\- unrelated settings boundaries.

Never store secrets in the project baseline. Record presence/location/type without copying secret values.

4\. SOURCE OF MUTATION  
Each mutation states one of:  
USER\_REQUEST  
CURRENT\_PRODUCT\_REQUIREMENT  
CURRENT\_AGENT\_REQUIREMENT  
BUG\_EVIDENCE  
EVAL\_FAILURE  
HOST\_CONSTRAINT  
EXPERIMENTAL\_HYPOTHESIS  
DONOR\_ADAPTATION

Donor adaptation must name donor/source and transformation. Convenience alone is not a source of authority.

5\. IMPLEMENTATION BOUNDARY  
Preferred rule for host state:  
IDEAL BODY SOURCE → generator/installer/update logic → HOST INCARNATION.

Direct host edits are acceptable only as exploration or emergency repair. If retained, they must be back-propagated into source/install logic before the run declares the embodiment reproducible.

6\. MUTATION EXECUTION  
Recommended sequence:  
OBSERVE  
→ BASELINE  
→ SPECIFY INTENDED EFFECT  
→ MAKE SMALLEST COHERENT CHANGE  
→ READ BACK / DIFF  
→ RUN TESTS  
→ VERIFY BEHAVIOR  
→ WRITE RECEIPT  
→ KEEP OR ROLLBACK.

The sequence may be iterated; it is not a finite-state ontology. Semantic judgment remains active at every step.

7\. VERIFICATION LEVELS  
FILE VERIFIED — expected files/diffs exist.  
INSTALL VERIFIED — host surfaces reflect intended generated state.  
BEHAVIOR VERIFIED — a fresh or independent execution actually demonstrates the capability.  
SURVIVAL VERIFIED — behavior survives restart/compaction/session boundary where relevant.  
PROJECT VERIFIED — capability works on a real mounted project.

Do not promote FILE VERIFIED to BEHAVIOR VERIFIED by assertion.

8\. ROLLBACK  
Rollback is mandatory for first-run host mutations.

Rollback may use:  
\- Git revert/reset for source project;  
\- backup copy restore for external host files;  
\- uninstall/update script generated by Proteus;  
\- exact inverse patch when proven safe.

After rollback, verify the restored state. A rollback command written but never capable of restoring actual files is insufficient.

9\. UNKNOWN AND CONFLICTS  
If a mutation depends on unresolved semantic authority:  
\- preserve competing claims;  
\- avoid destructive commitment;  
\- choose reversible experimental scope if useful;  
\- label result experimental;  
\- record what evidence would resolve it.

10\. PROMOTION OF EXPERIENCE  
A useful host-side adaptation is not immediately permanent product canon.

Promotion path:  
experience/deficit → evidence → source change proposal → tests → accepted source revision → generated incarnation → verified behavior.

If the adaptation is project-specific, keep it project-scoped. If host-specific, keep it in host adapter. Only genuinely cross-host behavior belongs in portable core.

11\. INSTALL RECEIPT — REQUIRED FIELDS  
\- receipt ID / RUN\_ID;  
\- timestamp;  
\- source revision;  
\- host version;  
\- installer/update version;  
\- files inspected;  
\- files changed;  
\- before/after hashes or diff references;  
\- requirement/source;  
\- tests performed;  
\- postconditions;  
\- PASS/FAIL/PARTIAL/NOT\_RUN per test;  
\- rollback location/procedure;  
\- unresolved issues;  
\- next recommended action.

12\. SELF-UPDATE CHECK  
For the first embodiment, one bounded second product improvement must use the just-created source→install→verify path.

Evidence required:  
\- deficit observed after first installation;  
\- source revision before/after;  
\- second install delta;  
\- verification result;  
\- receipt showing that the installed machinery participated in the development loop.

13\. PROHIBITED SHORTCUTS  
\- edit generated host files and declare source updated;  
\- overwrite user settings wholesale;  
\- copy secrets into repo/backups;  
\- convert failed behavior test into PASS because file exists;  
\- resolve semantic conflict by timestamp alone;  
\- delete historical alternatives to make the design cleaner;  
\- build broad infrastructure to avoid a small reversible test;  
\- preserve a clearly failed mutation merely to avoid rollback.

14\. FIRST-RUN SAFETY PRINCIPLE  
The first Proteus embodiment must be bold enough to become useful and bounded enough to be reversible. Safety comes from evidence, backup, verification and trustable change history rather than from preventing the agent from changing anything.
